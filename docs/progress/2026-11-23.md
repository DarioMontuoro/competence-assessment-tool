## 1. Il progetto (invariato)

Tool web di **valutazione delle competenze** (progetto d'esame, Prof. Bianchini, Università di Brescia, appelli giugno/luglio e settembre 2026). Backend TypeScript con NestJS e TypeORM, database **PostgreSQL** in locale. Autenticazione e utenti sono già nel template di partenza: qui ci si concentra sul backend della libreria `competency`, senza guardie.

### Dominio (dalle slide)

- **Competenza**: titolo, peso 1..5, insieme di sotto-competenze.
- **Sotto-competenza**: titolo, peso 1..5, input, azione, output, elenco di tool, method, skill.
- **Oggetto di osservazione**: uno per sotto-competenza, valutato con degli **indicatori**.
- **Indicatore**: descrizione e peso 1..5, valutato con un **rubric set**.
- **Rubric set**: 5 livelli (rank 1..5, descrizione opzionale). Caso yes/no: `no` = 1, `yes` = 5.
- **Test**: valuta una o più sotto-competenze. «Situation assessment» in testo libero che deve contenere luogo, tempo di somministrazione, materiale, numero di esaminatori e se devono essere esperti. Uno o più valutatori. Svolto da utenti valutati; ogni `test_execution` salva il punteggio. Output dell'utente: file con nome, descrizione, versione.
- **Ruoli**: Amministratore (matrice, import opzionale da file), Test designer (crea il test, assegna valutatori e utenti, può modificare oggetti e indicatori), Valutatore (assegna i rubric level), Utente (svolge il test).

### Formule delle slide

```
w          = Pcomp + Psub + Pind                 (per ogni indicatore)
ottenuto   = Σ w · RL
massimo    = Σ w · 5
percentuale = ottenuto / massimo · 100
```

Competenza = somma di ottenuti e massimi delle sue sotto-competenze (poi percentuale), **non** la media delle percentuali. Più valutatori sullo stesso indicatore: media oppure segnalazione di incongruenza.

## 3. Modifiche fatte alle entity (già applicate dall'utente)

- `TestExecution.test_score` e `max_score`: `nullable: true`, tipo `number | null` (l'esecuzione nasce prima della valutazione; `null` = non ancora valutata).
- `best_score_absolute` (in `BestSubcompetencyScore` e `BestCompetencyScore`): da `int` a `numeric` con `numericTransformer` (con la media tra valutatori l'ottenuto può essere decimale).
- `numericTransformer` verificato: gestisce `null`/`undefined` senza produrre `NaN`.

### Punti dello schema da ricordare

- `nullable: false` vale per la colonna della tabella che lo dichiara: i figli richiedono i genitori. L'ordine di creazione è dall'alto verso il basso: competenza / rubric set / tool / method / skill / designer / valutatore / utente valutato → sotto-competenza e rubric level → oggetto di osservazione → indicatore → test → esecuzione → valutazioni. Le regole del tipo "ogni sotto-competenza deve avere un oggetto di osservazione" non le impone il database: vanno nel service.
- `rubric_level_assignment.rubric_rank` è un intero libero, **non** una FK a `rubric_level`: la validazione (1..5, solo 1 e 5 nei set yes/no) è a carico del service.
- `Test.assessment_situation` è un unico `text`: la presenza di luogo, tempo, materiale, numero esaminatori ed esperti si controlla nel DTO.
- Le colonne `user_id` di `test_execution` e dei `best_*_score` contengono `evaluated_user.id`, **non** `evaluated_user.user_id`. Nei `where` usare sempre la relazione (`evaluated_user: { id }`).
- `ObservationObject → Subcompetency` è `OneToOne`: al massimo un oggetto per sotto-competenza.
- Le relazioni sono in snake_case: `evaluated_user`, `test_evaluator`, `observation_object`, `rubric_set`, ecc.

## 4. Modulo di scoring (fatto)

`computeScores(evaluations, options?) → ScoreReport`, funzione pura senza TypeORM.

```ts
interface IndicatorEvaluation {          // NON è un'entity: formato di scambio
  indicatorId; subcompetencyId; competencyId: number;
  competencyWeight; subcompetencyWeight; indicatorWeight: number;   // Pcomp, Psub, Pind
  yesNo?: boolean;
  ratings: readonly number[];            // un rubric_rank per valutatore; [] = non valutato
}
options: { tolerance?: number /*0*/; incomplete?: 'throw' | 'skip' /*'throw'*/ }
ScoreReport: { total, bySubcompetency, byCompetency, indicators,
               inconsistentIndicatorIds, missingIndicatorIds }
Score = { obtained, max, percentage }
```

Decisioni prese:

- Più valutatori: **media non arrotondata** (5 e 4 → 4,5) e segnalazione di disaccordo se max − min > tolleranza.
- Indicatore senza voti: errore di default (non si salva un risultato su un test incompleto); con `incomplete: 'skip'` viene escluso da ottenuto e massimo (per anteprime).
- Validazioni: pesi e voti interi 1..5; solo 1 o 5 nei set yes/no; indicatori duplicati rifiutati; una sotto-competenza non può stare in due competenze; **lo stesso peso per la stessa competenza e per la stessa sotto-competenza** (aggiunto in questa sessione).
- Percentuali **non arrotondate** nello scoring: si arrotonda solo quando si salva o si mostra.
- Con input vuoto: zeri e `percentage: 0`, senza divisione per zero.
- Set yes/no con valutatori in disaccordo (`[1, 5]`): media 3 e indicatore segnalato in `inconsistentIndicatorIds`. Sta al service decidere come gestirlo.

Esempio calcolato a mano usato nei test: C1 (peso 3) con S1 (peso 2: I1 peso 4 voto 5, I2 peso 1 voto 3) e S2 (peso 5: I3 peso 2 voto 1); C2 (peso 1) con S3 (peso 1: I4 peso 1 yes/no voto 5).
Risultati: S1 = 63/75 (84%), S2 = 10/50 (20%), S3 = 15/15 (100%), C1 = 73/125 (58,4%), **totale = 88/140 ≈ 62,857%**.

## 5. Mapper (fatto)

`buildIndicatorEvaluations(subcompetencies, assignments) → IndicatorEvaluation[]`: trasforma le entity caricate nell'array compatto per `computeScores`. Non tocca il database. Lancia un errore chiaro se una relazione non è caricata, se una sotto-competenza non ha oggetto di osservazione o indicatori, o se esiste un voto su un indicatore che non appartiene al test.

Query di caricamento da usare in `evaluateExecution`:

```ts
const execution = await this.executionRepo.findOne({
  where: { id: executionId },
  relations: {
    test: {
      subcompetencies: {
        competency: true,
        observation_object: { indicators: { rubric_set: true } },
      },
    },
    rubric_level_assignments: { indicator: true },
  },
});
const evaluations = buildIndicatorEvaluations(
  execution.test.subcompetencies,
  execution.rubric_level_assignments,
);
const report = computeScores(evaluations);
```

I test del mapper usano oggetti che imitano le entity: non verificano che il database restituisca davvero quella forma. Lo farà il test di integrazione.

## 6. Decisioni di architettura

- **Più service, non uno solo** (nessun vincolo organizzativo dal docente). Proposta, tutti in `src/lib/services/`:
  - `MatrixService`: competenze, sotto-competenze, rubric set, indicatori, tool/method/skill.
  - `TestService`: creazione test, assegnazione valutatori e utenti, output.
  - `EvaluationService`: `submitRating`, `evaluateExecution` (usa mapper + scoring).
  - `ResultsService`: best score e report di esecuzione.
  - `SeedService`: `seedExampleMatrix()`.
- Dipendenze a senso unico (es. `EvaluationService → ResultsService`, mai il contrario) per evitare dipendenze circolari. Le operazioni che scrivono più tabelle stanno in una sola transazione (`dataSource.transaction`), passando l'`EntityManager` tra i service se serve.
- `scoring/` è una cartella di funzioni pure, **non** un service: la importa chi ne ha bisogno. I mapper stanno fuori da `scoring/`, perché conoscono le entity.
- Essendo una libreria: il `DataSource` lo configura l'app, non la libreria. `typeorm` e `reflect-metadata` come `peerDependencies`. Niente `synchronize: true` in produzione (migration).
- Convenzioni dal service d'esempio del corso: DTO separati per create e update, interface `*ListItem` per le risposte (non restituire le entity), `NotFoundException` / `BadRequestException` / `ConflictException`, `handleDatabaseError` (codici Postgres `23505`, `23503`, `23514`, `23502`) da riusare come helper condiviso.

## 7. Come procedere (sessioni future)

Lavorare per **strati verticali**: ogni passo si scrive e si verifica con un test prima di passare al successivo.

### Passo 1: MatrixService + seed

- `createCompetency`, `createSubcompetency` (con tool, method e skill), `createObservationObject`, `createRubricSet` (5 livelli oppure yes/no con rank 1 e 5), `createIndicator`, più `find*` e `update*`.
- Validazioni: pesi interi 1..5; rank 1..5; nel set yes/no esattamente i livelli 1 e 5; l'indicatore richiede oggetto e set esistenti.
- La creazione di un'intera matrice va in transazione.
- `seedExampleMatrix()`: la matrice dell'esempio (§4), costruita usando i metodi del service. Non fissare gli id a mano (le sequenze di Postgres non avanzerebbero).
- Il file Excel di esempio del corso (Moodle, sezione «Registrazione elaborati») può servire da seed realistico.

### Passo 2: test di integrazione su Postgres

- Database separato `competency_test` con `dropSchema: true` e `synchronize: true`. Non usare `pg-mem` (supporta male `CHECK` e `numeric`).
- Verificare: salvataggio e rilettura della matrice con le relazioni; vincoli che scattano davvero (peso 6, secondo oggetto di osservazione per la stessa sotto-competenza, voto duplicato dello stesso valutatore).
- Test chiave: carica la matrice con la query di §5, passa il risultato a mapper e `computeScores` e verifica **62,857%**.

### Passo 3: TestService

- `createTest` (con sotto-competenze, designer e controllo del contenuto di `assessment_situation`), `assignEvaluators`, `assignUsers` (crea l'`evaluated_user` se manca e una `test_execution` con punteggi `null`), `addTestOutput` (unique su esecuzione + nome + versione).

### Passo 4: EvaluationService

- `submitRating(executionId, evaluatorId, indicatorId, rank)`: rank 1..5 (1 o 5 se yes/no); l'indicatore deve appartenere a una sotto-competenza del test; il valutatore deve essere assegnato al test; se esiste già un voto per la terna (indicatore, valutatore, esecuzione) lo aggiorna.
- `evaluateExecution(executionId)`: carica, costruisce l'array con il mapper, chiama `computeScores`, salva `test_score` e `max_score`, restituisce il report con le incongruenze.

### Passo 5: ResultsService

- Aggiornamento dei `best_subcompetency_score` e `best_competency_score` dopo ogni valutazione completata (un record per utente e sotto-competenza/competenza, grazie agli unique).
- **Arrotondare la percentuale a 2 decimali prima di salvarla**: la colonna è `numeric(5,2)` con `CHECK <= 100`, e un valore come `100.00000000000001` la violerebbe.

### Passo 6: controller e modulo

- Controller sottili divisi per area (matrice, test, valutazione, risultati), un metodo del service ciascuno, senza guardie. `competency.module.ts` con `TypeOrmModule.forFeature([...tutte le entity])`, i service tra `providers` e `exports`.
- Opzionale: import automatico della matrice da Excel.

## 8. Punti aperti da decidere

- **Formula**: `Pcomp` viene sommato su ogni indicatore, quindi la competenza pesa allo stesso modo su tutti i suoi indicatori. È coerente con le slide, ma conviene chiarirlo col docente.
- **Esecuzioni ripetute**: `(test_id, user_id)` deve essere unico? Se no, i best score vanno aggiornati a ogni valutazione completata, con regola «tieni il massimo».
- **Valutazione parziale**: valutare solo test completi (`incomplete: 'throw'`, default) oppure permettere anteprime con `'skip'`.
- **Yes/no in disaccordo**: bloccare il salvataggio o solo segnalarlo.
- **Sotto-competenza senza indicatori nel test**: oggi il mapper la rifiuta; da rivedere se serve consentirla.
- **`user_id` univoci** in designer e valutatore (un utente = un solo ruolo): rimandato a quando si collegheranno gli utenti reali.
- **Config e2e** (`apps/api-e2e/jest.config.cts`): errore su `module`/`moduleResolution`, da sistemare più avanti.
